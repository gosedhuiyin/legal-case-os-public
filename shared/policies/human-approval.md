# 律师批准门禁

任务默认成果、临时模板使用和学习保存见[材料访问与学习](material-access-and-learning.md)；执行深度见[执行配方](execution-recipes.md)。批准针对具体法律决定或交付阶段，不把所有文书初稿都变成完整案件管理。

## 哪个阶段需要批准

- 普通“生成文书”默认交付可编辑的 `internal_review` 初稿。可以直接使用本次明确指定的上传/本地模板；无需先建立完整 `case-state.json`、永久登记模板或取得G1/G2/G4。
- 内部稿不得伪称策略、证据提交或正式成稿已经批准。涉及请求范围、关键金额、特殊授权或实质立场的未决问题，集中澄清；可以先完成不依赖该决定的部分。
- 用户明确要求 `court_candidate` 时，按以下门禁核对当前策略、当前阶段拟提交证据及来源；已有有效且输入未变的批准直接复用。
- G4只在制作精确提交包时适用，不是交付单份可编辑初稿或法院候选稿的前置条件。

| 门禁 | 批准对象 |
|---|---|
| `G1_strategy` | 确定或实质改变诉讼主线、请求/抗辩及关键矛盾；法院候选稿须绑定有效策略 |
| `G2_evidence` | 当前阶段正式提交的精确证据集合；草稿中的参考材料不会因被阅读自动进入该集合 |
| `G3_draft_plan` | 复杂或重大风险正式文书中尚需律师决定的提纲/篇幅；低风险可合并进G1，不以篇幅或简单措辞反复阻断内部起草 |
| `G4_final` | 审阅通过文书组装形成的精确提交包快照或清单哈希 |
| `G5_external_action` | 精确包、具体动作和目标的外部授权；本套件没有G5执行器，批准不等于已执行 |

`SANITIZE` 继续适用[逐项清洁与原件保护](sanitization-and-originals.md)。长期保存学习成果另按[材料访问与学习](material-access-and-learning.md)确认具体候选内容；本次读取、提炼和应用不等于批准长期保存。

## 正式案件批准记录

使用正式状态门禁时，每个Approval绑定门禁、对象ID、版本/哈希、阶段、决定、理由、批准人、时间、状态、失效原因、精确 `scope_snapshot` 和规范化 `scope_hash`。同一事务追加唯一 `approval_granted` 收据；门禁、对象哈希、scope_hash与active批准一致，审计尾状态哈希须匹配当前case-state。

上游实质变化使相应批准失效并重新核验。校验、有状态清洁、组卷及打印生产单自行检查批准范围和审计收据。仅重算scope_hash不形成批准；没有状态的任务初稿也不能伪造正式Approval或声称门禁已经通过。

## “ok”批准语义

“ok”“可以”“就这个”只可确认当前唯一、刚展示、未变化且明确说明用途的一项候选。正式案件批准还须满足FocusContext、Approval与当前对象的版本/哈希一致。没有明确对象、多个候选、跨阶段、旧轮次、已变化或同时提出新修改时，先明确本次确认对象，不能泛化授权。

学习成果的短确认也只能绑定刚展示的具体候选内容；不能由AI补写用户没有作出的确认。批准不会扩展读取、修改、联网或外部动作权限。G4永不自动产生G5。
